# 一个人搞博客的心路历程

## 为什么要搞博客

说来也简单——想有个自己的地方，写点东西。

社交媒体太吵，笔记工具太私密，只有个人博客刚刚好。它是你自己的领地，想放什么放什么，想怎么排版就怎么排版。没有算法推荐，没有点赞焦虑，没有「仅自己可见」的尴尬，就是一个安静的角落。

有时候你会想：我在网上写的东西，到底属于谁？发在社交平台上，平台说封就封；存在笔记应用里，应用倒闭了数据就没了。但博客不一样——源码在你手里，部署在你手里，域名在你手里。只要 GitHub 还在，你的文字就在。

这不是偏执，是安全感。

## 技术选型：每一步都是选择题

一开始想用最简单的方案，后来发现每一步都是选择题，而且没有标准答案。

### 框架：Hexo 还是 Hugo？

Hexo 基于 Node.js，生态丰富，插件多，主题多，文档也全。Hugo 用 Go 写的，编译快，但主题和插件生态不如 Hexo。我日常写 Node.js 多，选 Hexo 顺手。

后来发现 Hexo 的坑也不少——生成速度慢、依赖管理混乱、插件之间偶尔冲突。但好在社区活跃，遇到问题搜一搜基本都有人踩过。

### 主题：NexT

试了几个主题，最后选了 NexT。理由很简单：干净、经典、不用改太多就能用。Pisces 配色方案自带侧边栏，适合我这种内容不多但想让页面看起来充实的人。

主题这东西，选了就不想换了。换主题意味着重新调配置、重新适配插件、重新排版——想想就头疼。

### 后台管理：hexo-pro

最开始每次写文章都要 SSH 到服务器，用 Vim 编辑 Markdown，然后手动部署。写了两篇之后就受不了了。

hexo-pro 是个不错的方案——有 Web 界面，能在线编辑文章、管理图片、一键部署。虽然它有不少 bug，但至少比 Vim 好用。

### 部署：GitHub Pages

免费、稳定、和 Git 工作流天然契合。对于个人博客来说完全够用。唯一的问题是国内访问速度一般，但也不是不能用。

## 踩过的坑

搭建过程远没有上面说的那么顺利。每一步「简单」的背后，都藏着一堆坑。

### hexo-pro 不支持自定义路径

hexo-pro 默认部署在 `/pro/`，但我的博客在 GitHub Pages 上，路径是 `/hexo-blog/pro/`。改了 `root` 配置后，路由全部 404，API 全部不通。

排查了一晚上，发现问题出在好几个地方：

- `index.js` 里的路由检测硬编码了 `/pro`
- body-parser 只匹配 `/hexopro/api`，改了路径之后请求体解析失败
- React Router 的 basename 也是硬编码的
- API 的 rewrite 中间件只改了 `req.url`，没改 `req.originalUrl`

最后写了一个 postinstall 补丁脚本，每次 `npm install` 自动修复所有问题。代码不复杂，但定位问题的过程很痛苦——因为你不知道到底有几个地方需要改，改了一个还有下一个。

### 播放器被页脚遮挡

音乐播放器用 `position: fixed` 固定在页面底部，结果被 hexo-pro 的 footer 盖住了。

一开始以为是 z-index 的问题，把播放器的 z-index 调到了 `2147483647`（32 位整数最大值），没用。后来发现是 CSS 堆叠上下文的问题——父元素的 `transform` 或 `filter` 会创建新的堆叠上下文，子元素的 z-index 再高也出不去。

改了布局方案，把播放器从全屏覆盖改成内嵌到内容区域，才彻底解决。

这个过程让我深刻理解了一件事：CSS 的布局不是你想的那么简单。`position: fixed` 不是真的「固定」，`z-index` 也不是真的「层级」。它们的行为取决于整个 DOM 树的结构。

### 部署时 git force push

有一次赶时间，用了 `git push --force`，结果把远程的旧文章覆盖了。本地还有备份，但远程已经丢了。

花了一个小时从本地回收站里恢复文件，重新提交推送。从那以后，我再也不用 force push 了。如果推送失败，先 `git pull` 解决冲突，再重新提交。

**永远不要 force push，除非你确定自己在做什么。**

### 网易云音乐 API 的坑

给博客加了音乐管理功能后，想集成网易云音乐搜索。一开始用的是 `/search` 接口，返回的数据结构和文档不一样——歌手字段叫 `ar` 不叫 `artists`，专辑叫 `al` 不叫 `album`。

后来发现 `/song/url` 接口根本拿不到播放链接（返回 null），只能用外链拼接的方式：`https://music.163.com/song/media/outer/url?id=xxx.mp3`。

这些坑不会写在文档里，只能靠试错和搜索别人的踩坑记录。

## 一个人搞的好处

虽然踩了很多坑，但一个人搞博客有几个实实在在的好处：

### 完全掌控

每一个像素、每一行代码都是你说了算。想把侧边栏播放器的封面做成圆形旋转？改 CSS 就行。想让文章保存后自动重新生成？改后端脚本就行。不需要跟任何人商量，不需要开评审会，不需要写需求文档。

这种掌控感在工作中很难体会到。

### 被迫学习

很多东西平时不会主动去学，但搞博客会逼着你学：

- CSS 堆叠上下文和 z-index 的真实行为
- HTTP Range 请求和 206 Partial Content
- Mermaid 图表的渲染机制
- GitHub Actions 的 CI/CD 流程
- Node.js 中间件的执行顺序

这些都是「知道有这么个东西」和「真正理解它」之间的差距。

### 成就感

看到自己的博客跑起来，那种满足感是用别人的东西体会不到的。尤其是当你解决了某个棘手的 bug，或者实现了一个有趣的 feature，那种「我做到了」的感觉——很纯粹。

有个朋友问我：「你搞这个有什么用？」我说：「没用，但挺有意思的。」

## 写在最后

一个人搞博客，本质上是一种「折腾的浪漫」。

它不会帮你找到工作，不会让你涨粉，不会带来任何直接的收益。但它会让你在某个深夜调试 CSS 的时候，突然觉得——

"这挺有意思的。"

然后继续折腾下去。

如果你也在犹豫要不要搞一个自己的博客，我的建议是：**搞吧，早搞早享受。** 不用追求完美，不用一步到位，先跑起来再说。

毕竟，折腾本身就是意义。
